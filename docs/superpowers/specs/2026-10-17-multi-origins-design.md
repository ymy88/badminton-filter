# 多出发地 — 设计文档

日期：2026-10-17
状态：已通过 brainstorming，待写实现计划

---

## 1. 目标

出发地不再固定为「家」「公司」两个，用户可以新增、改名、删除出发地。场景是**长期固定的几个地址**（例如「父母家」「健身房」），不是临时查一次就丢的地址。

### 已确认决策

| 项 | 决定 |
|---|---|
| 地址模型 | 所有出发地平等，「家」「公司」也只是列表里的普通条目，可改名、可删除 |
| 筛选语义 | 「并且」：每个出发地各一个通勤上限，填了上限的出发地都要满足；不填不限 |
| 表格列 | 每个出发地可选「显示成列」；不显示成列的出发地照样参与筛选，只是不占表格列 |
| 格子内容 | 保持完整格式「驾X分 / 公X分 / 步Xm」 |

### 非目标

- 不限制出发地数量。只在新增时提示成本：每个新出发地第一次全量算通勤，约「场馆数 × 3」次高德调用（目前约 1000 次）。
- 不做拖拽排序。顺序就是新增顺序。
- 不兼容旧的筛选字段 `homeCommuteMax` / `companyCommuteMax`（个人项目，不考虑历史兼容）。

## 2. 数据

### `origins` 表

```sql
CREATE TABLE IF NOT EXISTS origins(
  key TEXT PRIMARY KEY, name TEXT NOT NULL, address TEXT, lat REAL, lng REAL,
  show INTEGER NOT NULL DEFAULT 1,   -- 1 = 在表格里显示成列
  pos INTEGER NOT NULL DEFAULT 0);   -- 排列顺序，新增时取 max(pos)+1
```

- `db.py` 只改建表语句，**不写迁移代码**。
- 用户本地的 `games.db` 由人工执行一次 `ALTER TABLE` 加三列（先备份）：`home` 的 name 填「家」、pos 填 0，`company` 的 name 填「公司」、pos 填 1。key 保留 `home`、`company`，所以现有通勤缓存（`commute` 表 735 条）继续有效。
- 新出发地的 key 由后端生成：`"o" + uuid4().hex[:8]`。**key 不复用**：筛选条件里按 key 存了通勤上限，如果复用已删除出发地的 key，旧上限会被套到新出发地上。

### 各操作对通勤缓存的影响

| 操作 | `commute` 表 |
|---|---|
| 新增出发地 | 无（之后「算通勤」补算） |
| 只改名称 / 只改「显示成列」 | 不动 |
| 改地址（geocode 成功） | 删该 key 的全部行（与现在一致） |
| 改地址（geocode 失败） | 不动，旧地址和旧坐标都保留，该条报错 |
| 删除出发地 | 删 `origins` 行，并删该 key 的全部 `commute` 行 |

## 3. 接口

### `GET /api/origins`

按 `pos` 排序，返回列表：

```json
[{"key": "home", "name": "家", "address": "…", "has_coord": true, "show": true}, …]
```

### `POST /api/origins`

请求体：`{"origins": [{"key"?, "name", "address", "show"}, …]}`，是**完整列表**。

- 有 `key` 且存在：更新该条。
- 没有 `key`：新增。
- 库里有、列表里没有的 key：删除。
- 校验：`name` 去首尾空格后不能为空；新增条目的 `address` 不能为空；已有条目的 `address` 为空表示不改地址（与现在一致）。
- 地址 geocode 查不到：该条报错，其他条照常保存（与现在一致）。新增条目查不到地址时不入库。
- **算通勤进行中（`compute_lock` 被占）时，如果这次请求包含删除或改地址，整个请求返回 409**，提示「正在算通勤，等算完再改」。原因：后台线程开始时读了一份出发地坐标快照，算完会按旧坐标写回 `commute`，造成删除后又冒出孤儿行、或改地址后写入旧地址的通勤。只改名称或「显示成列」不受限制。
- 响应：与请求同顺序的结果列表，每项 `{"ok", "changed", "msg"?, "key"}`；`changed` 表示地址变了、需要重算通勤。

### 不改的部分

- `sync.py` 算通勤本来就按 `origins` 表里有坐标的出发地循环（`_origins_ll`、`incomplete_places`、`pending_count`），不用改。
- `/api/games` 的 `g["commute"]` 从按 `ORIGINS` 常量改为按 `origins` 表的全部 key 生成：`{key: {drive_min, transit_min, walk_m} | null}`。`app.py` 里的 `ORIGINS` 常量删除。

## 4. 主页

### 「设置地址」面板

- 每个出发地一行：名称框、地址框、「显示成列」勾选框、删除按钮、结果提示。
- 下方「+ 添加地址」新增一个空行，旁边写成本提示：「新地址第一次算通勤约 场馆数×3 次高德调用」。
- 「保存」把整个列表 POST 给后端。删除行时先 confirm：「删除『XX』会一起删掉它的通勤缓存，确定？」。确认后该行从面板里去掉，点「保存」才真正删除。
- 保存后重新拉 `/api/origins`，重建筛选框和表头；有任何地址变了 → 重新拉球局并启动算通勤（与现在一致）。409 时把提示显示在面板里。

### 左侧筛选

- 按出发地列表动态生成「XX通勤上限（分钟，按当前方式）」输入框，**所有出发地都有**，包括没勾「显示成列」的。
- 筛选条件存成 `commuteMax: {key: "分钟字符串"}`，随整份筛选条件存库。恢复时忽略已不存在的 key。
- criteria 里传 `commuteMax: {key: number}`（只含填了数的），`filters.js` 遍历它：值未知时看「含通勤未知」，超出上限剔除。

### 表格

- 表头按「显示成列」的出发地动态生成，列名「XX通勤」，排序键 `commute:<key>`。
- `filters.js` 的 `sortKey` 识别 `commute:` 前缀，按 `g.commute[key][mode]` 排序。
- 存下的排序列如果已不存在（出发地被删或被隐藏），回到默认的按开始时间排序（现有逻辑：`th.s[data-sort=…]` 找不到就保持默认）。
- 详情行（点开一行）加一行，列出**所有**出发地的完整通勤，例如「家：驾12分 / 公20分 / 步1.2km　父母家：未知」，隐藏列的出发地也能看到。
- 详情行 `colspan` 随列数变化。

### 提示条

- 没有任何出发地有坐标时显示，文字改为「请先在『设置地址』填出发地地址」。

## 5. 测试

- **pytest**（`tests/`）：
  - 新增出发地：入库，key 以 `o` 开头，pos 递增。
  - 只改名称 / 只改 show：通勤缓存不动。
  - 改地址：该 key 的通勤缓存被删，其他 key 的不动。
  - 删除出发地：`origins` 行和该 key 的 `commute` 行都删掉。
  - 新增条目 geocode 失败：不入库，其他条照常保存。
  - 名称为空：该条报错。
  - 算通勤进行中删除或改地址：409，库不变；只改名称：成功。
  - `/api/games` 的 `commute` 包含所有出发地的 key。
- **`tests/filters.test.mjs`**：
  - `commuteMax` 多个 key 同时生效（并且）；未填的 key 不限；未知值受「含通勤未知」控制。
  - `sortKey("commute:<key>")` 按该出发地当前方式排序，缺失排最后。
