# 多出发地 — 设计文档

日期：2026-10-17
状态：已实现

> **2026-10-17 修订**：「显示成列」不再是出发地的属性。`origins` 表、`/api/origins` 去掉 `show`；改为在列表上方「共 x / x 场」一行最右侧的「通勤列」下拉里勾选，隐藏的出发地 key 存在筛选条件 `hiddenOrigins` 里（和排序列一样是看表偏好，新出发地默认显示）。下文提到 `show` /「显示成列」勾选框的地方以此为准。

---

## 1. 目标

出发地不再固定为「家」「公司」两个，用户可以新增、改名、删除出发地。场景是**长期固定的几个地址**（例如「父母家」「健身房」），不是临时查一次就丢的地址。

### 已确认决策

| 项 | 决定 |
|---|---|
| 地址模型 | 所有出发地平等，「家」「公司」也只是列表里的普通条目，可改名、可删除 |
| 筛选语义 | 「并且」：每个出发地各一个通勤上限，填了上限的出发地都要满足；不填不限 |
| 表格列 | 每个出发地可选「显示成列」；不显示成列的出发地照样参与筛选，只是不占表格列 |
| 格子内容 | 保持完整格式「驾X分 / 公X分 / 步Xm」 |
| 定位方式 | 沿用球馆管理页：输入关键字 → 网页调高德 POI 搜索列出候选 → 用户点选；搜不到就手动填高德坐标或百度地图链接。不再用地理编码把文字地址直接换成坐标 |

### 非目标

- 不限制出发地数量。只在新增时提示成本：每个新出发地第一次全量算通勤，约「场馆数 × 3」次高德调用（目前约 1000 次）。
- 不做拖拽排序。顺序就是新增顺序。
- 不兼容旧的筛选字段 `homeCommuteMax` / `companyCommuteMax`（个人项目，不考虑历史兼容）。

---

## 2. 数据

### `origins` 表

```sql
CREATE TABLE IF NOT EXISTS origins(
  key TEXT PRIMARY KEY, name TEXT NOT NULL DEFAULT '', address TEXT, lat REAL, lng REAL,
  show INTEGER NOT NULL DEFAULT 1,   -- 1 = 在表格里显示成列
  pos INTEGER NOT NULL DEFAULT 0);   -- 排列顺序，新增时取 max(pos)+1
```

- `db.py` 只改建表语句，**不写迁移代码**。
- 用户本地的 `games.db` 由人工执行一次 `ALTER TABLE` 加三列（先备份）：`home` 的 name 填「家」、pos 填 0，`company` 的 name 填「公司」、pos 填 1。key 保留 `home`、`company`，所以现有通勤缓存（`commute` 表 735 条）继续有效。
- `address` 只用来显示位置，不再拿去查坐标：选 POI 时存 POI 名称加所在区和地址，例如「宜山路700号（徐汇区 宜山路700号）」；手动坐标存「手动坐标 经度,纬度」。
- 新出发地的 key 由后端生成：`"o" + uuid4().hex[:8]`。**key 不复用**：筛选条件里按 key 存了通勤上限，如果复用已删除出发地的 key，旧上限会被套到新出发地上。

### 各操作对通勤缓存的影响

| 操作 | `commute` 表 |
|---|---|
| 新增出发地 | 无（之后「算通勤」补算） |
| 只改名称 / 只改「显示成列」 | 不动 |
| 改位置（重新选了 POI 或填了手动坐标） | 删该 key 的全部行（与现在改地址一致） |
| 删除出发地 | 删 `origins` 行，并删该 key 的全部 `commute` 行 |

## 3. 接口

### `GET /api/origins`

按 `pos` 排序，返回列表（带坐标，面板里要给每个出发地放「地图」链接）：

```json
[{"key": "home", "name": "家", "address": "…", "lat": 31.17, "lng": 121.42, "show": true}, …]
```

### 搜索

复用球馆管理页的 `GET /api/amap/search?q=`（高德 POI 前 10 条），不新增接口。

### `POST /api/origins`

请求体：`{"origins": [{"key"?, "name", "show", "loc"?}, …]}`，是**完整列表**。`loc = {"address", "lat", "lng"}`，只有位置改了才带；坐标由前端给出（选中的 POI 坐标，或 `parseCoord` 换算后的高德坐标），后端不调高德。

- 有 `key` 且存在：更新该条。
- 没有 `key`：新增。
- 库里有、列表里没有的 key：删除。
- 校验：`name` 去首尾空格后不能为空；新增条目必须带 `loc`；`loc.lat`/`loc.lng` 必须是数字且 `venues.in_shanghai` 为真（与管理页手动坐标的校验一致）。
- 某条校验失败：该条报错，其他条照常保存。新增条目校验失败不入库。
- **算通勤进行中（`compute_lock` 被占）时，如果这次请求包含删除或改位置，整个请求返回 409**，提示「正在算通勤，等算完再改」。原因：后台线程开始时读了一份出发地坐标快照，算完会按旧坐标写回 `commute`，造成删除后又冒出孤儿行、或改位置后写入旧位置的通勤。只改名称或「显示成列」不受限制。
- 响应：与请求同顺序的结果列表，每项 `{"ok", "changed", "msg"?, "key"}`；`changed` 表示位置变了、需要重算通勤。

### 删掉的部分

- `commute.geocode` 只有 `/api/origins` 用，改完后没有调用者，连同 `tests/test_commute.py` 里它的测试一起删掉。`tests/test_app.py` 里按 geocode 写的出发地测试改写成按 `loc` 的新测试。

### 不改的部分

- `sync.py` 算通勤本来就按 `origins` 表里有坐标的出发地循环（`_origins_ll`、`incomplete_places`、`pending_count`），不用改。
- `/api/games` 的 `g["commute"]` 从按 `ORIGINS` 常量改为按 `origins` 表的全部 key 生成：`{key: {drive_min, transit_min, walk_m} | null}`。`app.py` 里的 `ORIGINS` 常量删除。

## 4. 主页

### 「设置地址」面板

- 每个出发地一行：名称框、当前位置（`address` 文字 + 「地图」链接，没定位时显示「未定位」）、「改位置」按钮、「显示成列」勾选框、删除按钮、结果提示。
- 点「改位置」在该行下方展开定位区，用 `locPicker` 组件（见下文「代码复用」），关键字初始值是出发地名称。选中候选或点「用这个坐标」后，定位区收起，该行的当前位置显示新位置并标「（未保存）」。
- 下方「+ 添加地址」新增一个空行并直接展开定位区，旁边写成本提示：「新地址第一次算通勤约 场馆数×3 次高德调用」。
- 「保存」把整个列表 POST 给后端。删除行时先 confirm：「删除『XX』会一起删掉它的通勤缓存，确定？」。确认后该行从面板里去掉，点「保存」才真正删除。
- 新增的行没选位置就点「保存」：前端直接提示「先给『XX』选位置」，不发请求。
- 保存后重新拉 `/api/origins`，重建筛选框和表头；有任何位置变了 → 重新拉球局并启动算通勤（与现在一致）。409 时把提示显示在面板里。

### 左侧筛选

- 按出发地列表动态生成「XX通勤上限（分钟，按当前方式）」输入框，**所有出发地都有**，包括没勾「显示成列」的。
- 筛选条件存成 `commuteMax: {key: "分钟字符串"}`，随整份筛选条件存库。恢复时忽略已不存在的 key。
- criteria 里传 `commuteMax: {key: number}`（只含填了数的），`filters.js` 遍历它：值未知时看「含通勤未知」，超出上限剔除。

### 表格

- 表头按「显示成列」的出发地动态生成，列名「XX通勤」，排序键 `commute:<key>`。
- `filters.js` 的 `sortKey` 识别 `commute:` 前缀，按 `g.commute[key][mode]` 排序。
- 存下的排序列如果已不存在（出发地被删或被隐藏），回到默认的按开始时间排序（现有逻辑：`th.s[data-sort=…]` 找不到就保持默认）。
- 详情行（点开一行）加一行，列出**所有**出发地的完整通勤，例如「家：驾12分 / 公20分 / 步1.2km　父母家：未知」，隐藏列的出发地也能看到。
- 详情行 `colspan` 随列数变化。

### 代码复用

选点区抽成组件 `locPicker`，放在 `common.js`，主页和球馆管理页共用。原因：手动坐标的说明和校验改过多轮（百度链接、去掉百度坐标、短链接、`uid=`），两份拷贝下次改时容易漏一边。

```js
locPicker(el, { query, onPick, onInput }) → { input, slot }
```

- `el`：容器元素，组件往里面渲染。`query`：关键字框的初始值。
- 组件内容：关键字框 +「在高德搜索」（回车也触发，调 `/api/amap/search`）；高德候选列表（名称、所在区、地址、「地图」链接，以及「搜索中」「没搜到」「搜索失败」三种提示）；手动坐标框（高德坐标或百度地图链接，边输入边预览换算后的高德坐标和「地图」链接）+「用这个坐标」按钮 + 说明文字（百度地图点开场馆后复制地址栏链接 / 高德坐标拾取器）。
- `onPick(p)`：点候选时 `p = {amap_id, name, lat, lng, district, address}`（即 `/api/amap/search` 返回的 POI）；点「用这个坐标」时 `p = {lat, lng}`（已是高德坐标）。手动坐标有错时组件自己在预览处显示 `coordError` 的说明，不调 `onPick`。
- `onInput(q)`：关键字框每次输入时调，管理页用它筛「已有统一球场」候选。
- 返回 `{ input, slot }`：`input` 是关键字框，调用方用来 focus；`slot` 是搜索框和高德候选之间的空容器，管理页把「已有统一球场」候选放进去（保持现在的布局：先看已有的，再看高德的）。
- `coordError` 和 `mapLink` 一起移进 `common.js`；`mapLink` 管理页其他地方也在用，照样导出。

**留在各自页面、不进组件的：**

- 管理页：编辑区原来的「保存坐标」按钮变成组件里的「用这个坐标」，点了直接归类，行为不变。「已有统一球场」候选列表；手动坐标的「名称」框（只有新建统一球场要用）；拿到 `onPick` 结果后调 `/api/venues/assign`（POI → `poi`，坐标 → `coord{name, lat, lng}`，名称取管理页的名称框，为空时提示「手动坐标需要名称」）。
- 主页：拿到 `onPick` 结果后只记到该行（POI → `address` 存「名称（区 地址）」，坐标 → `address` 存「手动坐标 经度,纬度」），等点「保存」再提交。

### 提示条

- 没有任何出发地有坐标时显示，文字改为「请先在『设置地址』填出发地地址」。

## 5. 测试

- **pytest**（`tests/`）：
  - 新增出发地：入库，key 以 `o` 开头，pos 递增。
  - 只改名称 / 只改 show：通勤缓存不动。
  - 改位置（带 `loc`）：坐标更新，该 key 的通勤缓存被删，其他 key 的不动。
  - 删除出发地：`origins` 行和该 key 的 `commute` 行都删掉。
  - 新增条目坐标不在上海 / 缺 `loc`：不入库，其他条照常保存。
  - 不带 `loc` 的已有条目：坐标和通勤缓存都不动。
  - 名称为空：该条报错。
  - 算通勤进行中删除或改位置：409，库不变；只改名称：成功。
  - `/api/games` 的 `commute` 包含所有出发地的 key。
- **`tests/filters.test.mjs`**：
  - `commuteMax` 多个 key 同时生效（并且）；未填的 key 不限；未知值受「含通勤未知」控制。
  - `sortKey("commute:<key>")` 按该出发地当前方式排序，缺失排最后。
- **浏览器回归**（管理页改用组件后）：搜索 → 选高德候选；输入关键字时「已有统一球场」候选跟着变 → 选已有统一球场；手动坐标（高德坐标、百度链接、百度短链接报错、精度不够报错）→ 保存。主页：新增出发地 → 搜索选点 → 保存 → 出现新列和新上限框 → 算通勤；改名、隐藏列、删除。
